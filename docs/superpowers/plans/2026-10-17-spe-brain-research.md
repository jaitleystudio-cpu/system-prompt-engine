# SPE brain evolution: evidence-bound research and integration plan

17 October 2026 · Asia/Kolkata · Status: RESEARCHED PROPOSAL, NOT IMPLEMENTED OR RELEASE QUALIFIED

## Decision

Build a versioned, independently evaluated improvement pipeline for SPE's knowledge, prompt strategies, model routing and bounded software skills. Run discovery and experiments daily; promote only candidates that demonstrate an accepted benefit without material regressions. Keep the working brain when no candidate qualifies. Foundation-model training and unrestricted production self-rewriting are not the recommended starting point.

This can remove routine daily founder supervision. It cannot guarantee that an arbitrary future failure never requires an owner, that improvements happen every day, or that SPE becomes first in every country. Market leadership requires observed customer outcomes and adoption, not an increasing version counter or benchmark alone.

## Mission, current custody and boundaries

User wants SPE to become more capable through automatic brain/version updates and to operate A to Z without daily supervision. Preserve browser-local processing, cached resilience, free product scope and privacy boundaries. Do not use private prompts or derivatives for advertising. No payment enablement, deployment, new account, external message, scheduled automation or paid model call is authorized by this research deliverable.

Fresh read-only custody: clean local feature head 5db39687161be946eae6ebe8be1ab3f7833848ec. Inspected relevant source seams, not the entire repository. New files already exist for autonomous operations, model-history/registry transitions and evaluator protection. Their names/comments are evidence of intended architecture, not independent qualification. Examples include local JSON persistence without cross-process transaction semantics in SharedRunCoordinator and a token-overlap metric described as semantic similarity. Such seams need actual behavior tests before assuming shared durable locking or multilingual semantic evaluation.

Do not create a second competing orchestration/model-authority subsystem. Extend existing owners and separately test their storage, failure and authorization boundaries. No claim that earlier defects remain unchanged across this newer head without a dedicated replay.

## 1. Define the brain as independently versioned components

| Component | What can improve | Update mode and limit |
|---|---|---|
| Trusted operating policy | Release authority, privacy, spending and tool permissions | Fixed outside optimizer write scope; changes are separate owner decisions. |
| Knowledge snapshots | Official model docs, API contracts, public approved reference content | Daily/event-driven ingestion, source and timestamp bound, quarantine before use. |
| Model registry | Exact provider API IDs, region/account access, lifecycle, capabilities | Discover -> callable under authorized account -> task-qualified -> eligible. Absence alone is not retirement. |
| Prompt strategies | Model/task-specific instructions and examples | GEPA or comparable candidate search in sandbox; no authority to alter user requirements. |
| Model routing | Which qualified model/prompt serves a given task/language/budget | Select on measured quality/cost/latency, retain fallback and constrain data egress. |
| Skill/repair library | Tested workflows for recurring failure classes | Add only reproducible, scoped, independently tested skills; not self-reported successes. |
| Failure memory | Evidence of what failed, why and under what conditions | Structured, deduplicated, expiring/version-scoped cases with origin and applicability. |
| Evaluation policy | Protected invariants, hidden cases, measurement methods | Separate writer/credentials from candidate generator; checksum alone is not isolation. |
| Optional trained weights | A specific model's learned parameters | Later, only with lawful data, budget and capability-retention evaluation; not equivalent to a knowledge sync. |

Calling a provider's new model does not retrain SPE's own weights. Updating retrieval data changes available information, not necessarily reasoning quality. A bigger prompt library is not automatically a better brain.

## 2. Research findings and limits

| Evidence | What it supports | What it does not support |
|---|---|---|
| DSPy GEPA official guide and GEPA 2025 paper | Metric-guided prompt evolution using failure feedback and train/validation splits. Guide explicitly requires a separate final test set. | Guaranteed transfer to every task/model/language or free optimization. |
| Darwin Gödel Machine, v3 | Archived candidate agents and empirical self-modification can improve bounded coding benchmarks with frozen foundation models. | Its paper explicitly does not demonstrate training a new foundation model; experiments used sandboxing and human oversight. |
| PACEvolve, pinned v2, January 2026 | Memory/context pruning, backtracking and diversity address context pollution and search stagnation in evaluated evolutionary tasks. | General proof of safe daily production self-improvement or direct SPE performance. |
| RouteLLM | Preference-trained routing can explore a quality/cost tradeoff on evaluated models/tasks. | Any exact savings for SPE or that historical strong/weak model labels remain true. |
| Reusable holdout, Science 2015 | Repeated adaptive evaluation can invalidate naive testing; protected query strategies matter. | A plain repeatedly reused private test set magically remains unbiased. |
| AgentPoison | Retrieval/memory poisoning is a demonstrated attack class even without weight training. | A keyword blacklist makes all retrieved text safe. |
| Global MMLU, ACL 2025 | Cultural context and translation quality can change multilingual rankings; language translation alone is insufficient. | Knowledge-question scores certify SPE product usability or country market leadership. |

## 3. Daily improvement loop

1. **Discover:** official release feeds/APIs/docs and authorized aggregate failure signals. Record fetched bytes, URL, timestamp, parser version and rights/use limits. Competitor claims are research inputs, not ground truth.
2. **Quarantine:** remove credentials/private material, reject executable directives, label conflicts and unverified claims. Store raw reference data separately from operating policy. External text has no tool or release authority.
3. **Diagnose:** turn reproducible product failures into scoped tasks: exact input, expected invariants, failing output, environment/provider revision and applicable language/task.
4. **Generate:** bounded candidates changing one component where practical: same model/new prompt; new model/current prompt; new routing; new retrieval snapshot. Preserve causal attribution.
5. **Evaluate:** compare incumbent and candidates under matched examples, resource budget, tool access and model snapshots. Use randomized order and repeated trials for nondeterministic outputs. Deterministic checks and external/executable truth take priority over LLM self-grading.
6. **Select:** keep qualified candidates in an archive; identify best per supported slice, not one universal winner. Stop stagnating searches, reset polluted context and use a small measured diversity budget.
7. **Package:** immutable brain manifest binding all component digests, policy/evaluator version and evidence. Build once; qualify and deploy the same artifact.
8. **Shadow/preview:** approved synthetic or consented traffic only. Shadow calls are real cost/data egress; prohibit them on private content without authorization. No assumption that public traffic implies permission to duplicate prompts to another provider.
9. **Promote:** only allowed changes with signed trusted provenance, qualified artifact and actual deployment evidence. Use measured canary when hosting and traffic support it; otherwise preview plus controlled release switching. Never call a preview a measured 1% rollout.
10. **Observe/recover:** measure behavior, serving artifact, errors, costs and relevant task outcomes. Roll back to a known-good compatible artifact if policy conditions fail. A database migration needs its own compatibility/recovery method; code rollback alone is insufficient.

Desired daily start can remain 02:17 IST, with recovery deadlines at 03:00 and 06:00 IST. These are proposed operational targets. Event triggers reduce waiting for urgent provider changes. One durable job authority must coordinate native/cloud dispatches; two independent cron writers are not a reliability strategy. The primary runner should not depend on an awake Mac for public-service availability.

Create a BrainRelease manifest rather than bumping one global number because a clock fired. Illustrative fields, not actual releases:


Separate development, qualified and deployed channels. Unknown receipt fields never become default PASS. Use proper secret custody and authenticated build/execution identity; public/default HMAC keys cannot authenticate production. Consider established TUF update metadata for version/freshness/target integrity, with authorized rollback expressed as a new auditable metadata transition. TUF protects update delivery; it does not prove prompt quality or factual correctness. Offline clients retain compatible last-known-good features and expose staleness honestly rather than losing exports.

Weight-model, retrieval, prompt and router versions must be separable so an incident can revert the responsible component. Provider aliases can drift despite a frozen local manifest; record provider revision where available and run contract/outcome checks when that behavior changes. Retired models require a qualified compatible fallback, not arbitrary newest-model substitution.

## 5. Acceptance design

Use four distinct resources:

- **Training/development failures:** candidate generation can inspect them.
- **Selection validation:** chooses candidate under a bounded search budget; not reported as untouched proof.
- **Protected audit:** candidate generator cannot read examples, fixtures or detailed outcomes. Limit queries, use predeclared sequential/multiple-comparison policy and replenish representative independent cases. Repeated pass/fail signals still leak information.
- **Permanent regression corpus:** known critical failures must never reappear in accepted candidates; useful for retention, not new generalization claims.

Use grouped/temporal splits to avoid near-duplicate templates crossing partitions. Synthetic tests help coverage but cannot replace native user tasks or domain truth. If an audit case is disclosed for repair, move it to development/regression and replenish the audit pool independently.

Hard checks: preserve all confirmed requirements; valid Unicode/serialization; correct tool/data boundaries; no unauthorized disclosure/egress; no evaluator changes; genuine artifact/deployment binding; bounded cost/retries; working restore; compatibility with core free/cached flows. Zero observed violations on these tests is a finite-sample result, not proof of universal safety.

Optimization goals: task completion, first-try usable output, correction effort, latency, cost per successful task and supported-locale quality. Do not let a high aggregate compensate for privacy failure or major regional regressions. Define tolerance and confidence requirements per slice before seeing candidate results.

For the pilot, choose a minimum practical effect (for example a few percentage points task success, or reduced cost with demonstrated quality noninferiority) only after measuring baseline variance and deciding budget. No arbitrary fixed test count or p-value guarantees success. Use paired analyses, seed/model revision receipts, confidence intervals and a correction policy for many candidates. Low sample volume is INCONCLUSIVE, not PASS. Automatic safe hold is the default for inconclusive evidence.

## 6. Country-by-country competitiveness

Start with three customer jobs and a manageable set of supported language/region slices, then expand based on demand and reliable outcomes. Examples of useful SPE jobs: a beginner turns a plain brief into a faithful prompt; a developer exports a model-compatible instruction contract; a team reuses a prompt with preserved constraints. Final segment selection requires customer evidence, not a claim that all three are already best commercial choices.

Build a capability matrix across language, task, device/network, provider availability and domain. Include code switching, right-to-left UI, local date/number/currency conventions, assistive interaction and culturally relevant examples. Language is not country: Spanish or Arabic support does not certify every Spanish- or Arabic-speaking market. A large language model benchmark is supplemental, not a substitute for actual SPE tasks.

Use blinded comparisons with relevant alternatives on identical briefs, task-time and cost. Measure completion, corrections, returning use and willingness to pay in real cohorts. Any native review/customer panel must be separately arranged with appropriate permission/budget; this proposal does not contact people or purchase services. Public leadership claims must name the task, locale, evaluation date, comparison set and uncertainty. Do not publish first-place-in-every-country claims without evidence.

## 8. Phases and decisive experiments

These are dependency gates, not promised calendar deadlines.

**Phase A — trust and observability.** Test external outcome reconciliation, protected signing identities, evaluator isolation and transactional leases. Fault-inject duplicate triggers, stale worker, corrupt state, lost network response and interrupted publication. Gate: no duplicate external effects in these controls, no false production classification, accurate recovery receipts. Workload/budget agreed before external tests.

**Phase B — evidence baseline.** Establish rights-cleared task sets, grouped splits, supported slices and current champion. Record correctness, correction effort, latency, provider costs, coverage gaps and cold/warm device conditions. Gate: reproducible baseline and held-out authority outside agent control.

**Phase C — bounded brain experiments.** Compare (1) no-op/current champion, (2) simple manual/rule baseline, (3) matched-budget random candidate search, (4) GEPA, (5) retrieval refresh alone, (6) new model/current prompts, (7) new routing. Start on a few workflows; otherwise a gain cannot be attributed to any component. Use small candidate budgets and real model-price ceilings. Gate: independent task improvement/noninferiority and critical regression retention. NOT RUN in this research turn; no paid optimization authorized.

**Phase D — autonomous delivery.** Promote allowlisted data/prompt/routing changes first. Preview/canary, validate actual serving digest, automatically revert failed candidates and record no-op days. Gate: rehearsed rollback and interrupted-run recovery on the actual hosting interface.

**Phase E — controlled skill/code evolution.** Repair agents may modify bounded skills/code in disposable environments, not policy/test authority. Use a diverse archive and stop stagnating searches. DGM/PACEvolve are inspiration for experimental controls, not justification for unrestricted production recursion.

**Phase F — optional fine-tuning.** Only after evidence shows a stable failure that retrieval/prompt/routing cannot solve. Curate lawful consented data; train an owned/licensed model under budget; compare with prompt-only and untrained baseline; test catastrophic forgetting, privacy leakage and broad capability retention. Foundation-model pretraining is not a prerequisite for SPE product strength.
