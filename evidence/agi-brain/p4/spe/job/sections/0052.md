## 6.3 Core Library and Universal ABI Free Access Policy Explanation — Clarification on the Scope of Core Library Coverage

**6.3 Core Library and Universal ABI Free Access Policy Explanation** The core library and Universal Abstract Base Interface (ABI) constitute one of the foundational pillars upon which the SPE system is built, ensuring a consistent and interoperable environment for all modules within the architecture. This section aims to clarify the scope of access and use permissions granted by this policy. ### 6.3.1 Overview The core library represents the backbone of the SPE ecosystem, providing essential functionalities without requiring external dependencies. The Universal ABI is designed to facilitate seamless communication between these components, enabling them to interact harmoniously within a unified system architecture. By adhering to the principles outlined in the LVT-3 policy, developers can leverage this framework freely and securely. ### 6.3.2 Scope of Core Library Coverage The core library and Universal ABI are designed with several key accessibility policies in mind: 1. **Local Python Environment**: The core library is accessible within a local Python environment without requiring any external dependencies or hosting solutions. This ensures that all development and testing activities remain confined to the project’s own infrastructure, maintaining control over the entire development lifecycle. 2. **Documentation and Conformance JSONL Files**: All documentation and conformance JSONL files are included in the core library, facilitating transparency and ensuring compliance with established standards and guidelines. These files serve as a comprehensive resource for developers looking to integrate the SPE system into their projects seamlessly. 3. **Free/Open Dependencies**: The library includes free/open dependencies such as `jsonschema`, which is essential for validating data structures within the SPE environment. This approach not only simplifies integration but also ensures that all components remain independent of proprietary or expensive third-party libraries. 4. **Documentation and Conformance JSONL Files**: These files are included in the core library, providing a clear roadmap for developers to understand how different modules interact with each other. This helps in building more cohesive systems where individual modules can be easily integrated into existing projects without significant modifications. 5. **Free Python Environment**: The free local environment is crucial for developing plugins and extensions that integrate seamlessly with the SPE system. It ensures compatibility across all versions of the software, reducing the need for extensive testing or maintenance, thereby minimizing potential issues and enhancing overall reliability. ### 6.3.3 Forbidden Cost Vectors The LVT-3 policy explicitly prohibits certain cost vectors from being included in the core library: 1. **Paid Package Registry Deps**: The use of any paid package registry dependencies is strictly forbidden. This ensures that all components remain free and open, fostering a community-driven development environment. 2. **Paid API Keys (LLM, Search, Billing)**: Similarly, access to paid LLMs, search APIs, or billing systems is not permitted within the core library. This restriction aims to maintain the integrity of the free and open-source nature of the SPE ecosystem. 3. **Hosting / SaaS Required for Proofs**: Hosting solutions or Software as a Service (SaaS) platforms are also excluded from the core library policy. This ensures that all proof activities remain offline, allowing developers to focus on developing robust systems without external dependencies. 4. **Prompt Marketplace in Core**: The prompt marketplace is completely prohibited within the core library. This restriction aims to keep the SPE system focused on its primary functions and avoids any potential conflicts with external marketplaces or sales platforms. 5. **Ad Targeting / Telemetry Sales**: Lastly, ad targeting mechanisms and telemetry sales systems are explicitly forbidden. This policy ensures that all communication remains transparent and ethical within the development process, avoiding unnecessary complications and ensuring fair distribution of resources. ### 6.3.4 Proof Posture The proof posture for the core library is defined as a reproducible offline environment on a clean checkout with `python -m pytest`. This means that any developer can verify the integrity of the SPE system by running their own tests locally, adhering to the principles outlined in the LVT-3 policy. This approach ensures that developers remain in control throughout the development process and maintain high standards for quality assurance.
