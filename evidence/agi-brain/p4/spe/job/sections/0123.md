## 13.4 Conditions for Hard Rules Compliance: Free Core, No Paid Expenditures — Criteria for Mandatory Exclusions

**13.4 Conditions for Hard Rules Compliance: Free Core, No Paid Expenditures — Criteria for Mandatory Exclusions** In accordance with the **Zero Cost Product Law (ZCPL)**, which is a fundamental cornerstone of SPE's design philosophy, developers must adhere to stringent guidelines that prevent any form of commercial expenditure or external dependency on paid services. This adherence ensures that the core library and universal ABI remain free for all users, enabling researchers to focus solely on creating meaningful research content without financial constraints. ### Criteria for Mandatory Exclusions For compliance with the ZCPL’s **Free Core** rule, developers must ensure that they use only locally installed dependencies and do not include any paid package registry dependencies. Additionally, no paid API keys (LLM, search, billing) or hosting services are permitted in the core library. #### Implementation: Adherence to Hard Rules To comply with these rules, developers should follow several key criteria: 1. **Local Python**: Ensure that all development and testing activities remain within a local Python environment without relying on external packages or registries. 2. **Free Dependencies**: All required dependencies must be declared as free/open projects within the project’s `pyproject.toml` file. This includes libraries such as `jsonschema`, which is essential for schema validation, but it should only be included if it is truly necessary and available locally without requiring external services. 3. **Documentation and Conformance**: Maintain comprehensive documentation and conformance JSONL files to ensure reproducibility of proof runs offline. ### Forbidden Cost Vectors While the core library must adhere strictly to the ZCPL, certain additional components may not be allowed under specific circumstances: #### Allowed — Local Python, local fixtures, local tempfile adapters already in-tree This list includes all necessary tools and configurations that can be implemented locally without external dependencies. For instance, fixtures for testing purposes are essential but should remain as part of the development environment. #### Forbidden Cost Vectors 1. **Paid Package Registry Deps for Core** - This rule prohibits any paid package registry dependencies in the core library to ensure it remains free and accessible. 2. **Paid API Keys (LLM, search, billing)** - Developers are strictly forbidden from using any paid APIs or LLMs within the core library. This includes all query-based services that require payment for access. 3. **Hosting / SaaS Required for Proofs** - Hosting and Software as a Service (SaaS) solutions must be avoided entirely when running proofs, ensuring that all resources are local and available to all users. 4. **Prompt Marketplace in Core** - The core library cannot include any marketplaces or prompt sales mechanisms. 5. **Ad Targeting / Telemetry Sales** - This rule strictly prohibits the inclusion of advertising SDKs or user-targeting ad pipelines, ensuring that research is conducted without commercial bias. ### Proof Posture For compliance with the ZCPL’s **Proof posture** requirement, all proof runs must remain reproducible offline on a clean checkout. This means that no external dependencies or services should be used during the development phase of proofs to ensure that every piece of code and configuration can be tested independently. #### Criteria for Compliance 1. **Local Python**: Ensure that all proofs are conducted within a local Python environment. 2. **Free Dependencies**: Any required dependencies must be included in the `pyproject.toml` file as free/open projects. 3. **Documentation and Conformance JSONL**: Maintain comprehensive documentation and conformance JSONL files to ensure reproducibility. ### Conclusion By adhering to these stringent guidelines, developers can create meaningful research content without violating the ZCPL’s hard rules. This ensures that SPE remains a cost-effective and affordable platform for researchers, allowing them to focus solely on their scientific contributions while maintaining control over their development environment. Compliance with these rules is essential for ensuring affordability and ease-of-use in SPE development. ### GLOSSARY (Revisited) - **CCR = Counterfactual Challenge Record** - A record of experiments designed to test counterfactual scenarios. - **CSC = Counterfactual Specification Closure** - The process of synthesizing a closed specification that is equivalent to the original model but with some specified changes. - **FAR = False Acceptance Rate** - The rate at which a system fails to correctly accept inputs under certain conditions.
